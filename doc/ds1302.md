# DS1302 RTC memory-mapped registers

The DS1302 controller is decoded at **`$F28000–$F2BFFF`** (16 KiB).
Its clock/calendar and battery-backed RAM registers are accessed through the
same memory interface. Each selected CPU data access performs a serial
transaction with the DS1302. A registered CPU-bus adapter holds the CPU until
the transaction finishes and its result is ready.

## Access format

- Use byte accesses (`move.b`) at **even addresses**.
- The device uses the upper byte of the 16-bit data bus, qualified by `UDS`.
- Registers are spaced two bytes apart: register index `n` is at `$F28000 + 2*n`.
- Word accesses also select the device, but only bits 15–8 carry its data.
  Bits 7–0 read as zero and are ignored on writes.
- Only address bits 6–1 reach the controller, so the register layout repeats
  every `$80` bytes throughout the decoded window. Use the first copy below.

For example, writing byte `$55` to `$F28040` is equivalent to writing word
`$5500` to that address. A word read then returns `$5500`.

## CPU-bus handshake and serial engine

[`Ds1302Device.scala`](../hw/spinal/rt68ice/io/Ds1302Device.scala) handles the
CPU-bus transaction: it captures the address, direction, and write data, then
holds a registered request until it has observed `BUSY` assert and deassert.
Completion and read data are synchronized back into the system clock domain.
The result stays latched until the CPU leaves the transfer. Address or direction
changes also identify consecutive transfers when the CPU keeps its strobes
asserted. The bus controller qualifies selection with CPU data-read/data-write state
and the adapter requires the upper-byte strobe (`UDS`).

[`DS1302.vhd`](../hw/vhdl/DS1302.vhd) handles the slower serial protocol:
CE, SCLK, command/data shifting, and binary/BCD conversion. These are separate
responsibilities; its serial sequencing does not replace the CPU-bus handshake.

Previously, combinational bus signals directly drove the VHDL request input,
whose edge clocks its asynchronous `BUSY` logic. The registered adapter prevents
transient selections from starting requests that disappear before the serial
engine samples them. The adapter change resolved the observed `rtc_get` stalls
on hardware without diagnostic prints or software delays.

This fix requires an updated FPGA bitstream; rebuilding the applications alone
does not update the interface. Build and load it into FPGA RAM with:

```sh
make rt68ice.bit
make prog
```

## Register map

All addresses and offsets in this table are hexadecimal. Numeric ranges are
decimal unless prefixed with `$`.

| CPU address | Offset | Register | Value / purpose |
| --- | --- | --- | --- |
| `$F28000` | `$00` | Seconds | 0–59 while running normally |
| `$F28002` | `$02` | Minutes | 0–59 |
| `$F28004` | `$04` | Hours | 0–23 in 24-hour mode |
| `$F28006` | `$06` | Day of month | 1–31 |
| `$F28008` | `$08` | Month | 1–12 |
| `$F2800A` | `$0A` | Day of week | 1–7; software chooses the weekday convention |
| `$F2800C` | `$0C` | Year | 0–99; century is managed by software |
| `$F2800E` | `$0E` | Write protection | `$00`: enable writes; `$80`: protect clock and RAM registers |
| `$F28010` | `$10` | Trickle-charger control | Raw control byte; leave unchanged for the RAM test |
| `$F28012–$F2803C` | `$12–$3C` | Reserved | No ordinary registers |
| `$F2803E` | `$3E` | Clock burst command | Not an ordinary register; this controller does not implement a full clock burst |
| `$F28040` | `$40` | RAM byte 0 | Raw byte, `$00–$FF` |
| `$F28042` | `$42` | RAM byte 1 | Raw byte, `$00–$FF` |
| … | … | … | … |
| `$F2807C` | `$7C` | RAM byte 30 | Raw byte, `$00–$FF` |
| `$F2807E` | `$7E` | RAM burst command | Not an ordinary register; this controller does not implement a full RAM burst |

RAM byte `n`, for `n = 0..30`, is at **`$F28040 + 2*n`**.

The FPGA constructs the DS1302 read/write command automatically. Software reads
and writes the same CPU address for a given register; the datasheet's serial
command bytes are not CPU addresses.

The native chip register definitions are described in the
[DS1302 datasheet, Table 3](https://www.analog.com/media/en/technical-documentation/data-sheets/DS1302.pdf).

## Binary and BCD conversion

The imported VHDL automatically converts registers 0–6 (seconds through year)
between CPU-side binary values and the DS1302's BCD representation.

For example, to set normal seconds to decimal 45:

```asm
move.b  #45,$00F28000       ; CPU byte $2D; controller sends BCD $45
```

A normal seconds value of 45 reads back as byte `$2D`, or word `$2D00`.
Write protection, charger control, and RAM are raw bytes with no conversion.

The VHDL converts the **whole byte**, including any flag bits. The seconds
clock-halt flag and the hours 12-hour/AM-PM flags therefore do not have a
transparent raw-bit interface. The normal ranges above assume the clock is
running in 24-hour mode. Use RAM for the initial communication test.

## Clock Halt (CH) bit and starting timekeeping

The **Clock Halt (CH) bit** is bit 7 of the DS1302's native seconds register.

| CH | Effect |
| --- | --- |
| `0` | The timekeeping oscillator runs and the time/date advance. |
| `1` | The oscillator stops and the time/date stop advancing, reducing power consumption. |

The initial CH value after first power-up is undefined, so software should
initialize the clock and clear CH. See the **Clock Halt Flag** section of the
[DS1302 datasheet](https://www.analog.com/media/en/technical-documentation/data-sheets/DS1302.pdf).

The module's **32.768 kHz crystal oscillator** keeps time; CH controls this
oscillator. The FPGA's **250 kHz serial clock (SCLK)** transfers commands and
data independently. RAM reads and writes can therefore work while timekeeping
is halted.

For example, native seconds byte `$81` means **CH = 1, seconds = 01**. Because
the VHDL converts the entire byte through its BCD-to-binary table, software
sees `$51` (decimal 81), displayed by the monitor as **`5100`**. This indicates
a halted clock, rather than 51 seconds.

Writing zero to the seconds register sends native `$00`: seconds become zero
and CH is cleared. With write protection disabled:

```text
write F2800E 0000
write F28000 0000
```

Writing `8000` does **not** set CH through the current interface. The VHDL
converts CPU byte `$80` (decimal 128) to native BCD `$28`, leaving CH clear.
Raw bit masks from the chip datasheet cannot be applied directly to this
converted register.

To **stop** the oscillator, supply CPU byte `$50` (decimal 80), which the
conversion table maps to native `$80`: CH = 1 and seconds = 00.

```text
write F2800E 0000
write F28000 5000
dump F28000
```

The first word should remain `5000` on subsequent reads. To restart, use
`write F28000 0000`; this clears CH and starts again from zero seconds.
Both commands reset the seconds value. The conversion only generates native
bytes `$00–$99`, so it cannot represent every CH-plus-seconds combination;
in particular, halting while preserving seconds 20–59 is not supported by
this interface.

If the clock/calendar values are uninitialized, set a valid date and time
before starting the oscillator. This example sets **1 January 2026, Thursday,
00:00:00**, with Monday = 1. Set seconds last to clear CH and start counting.

```text
write F2800E 0000
write F28002 0000
write F28004 0000
write F28006 0100
write F28008 0100
write F2800A 0400
write F2800C 1A00
write F28000 0000
```

`1A00` supplies binary decimal 26 for the year; the controller sends BCD `$26`.
Run `dump F28000`, wait a few seconds, and repeat. The first word should
increase. The monitor displays hexadecimal binary values: 10 seconds appears
as `0A00`, and 20 seconds as `1400`. Rewriting seconds restarts the seconds
count, so use reads when checking that it advances.

## Read/write test from the ROM monitor

The monitor's `write` and `dump` commands use **16-bit words**, and their arguments
are hexadecimal. Put the desired RTC byte in the upper half of the word.

This test overwrites RAM byte 0 and clears write protection. First record their
original values if they need to be restored: the first word of each dump is the
value at the requested address.

```text
dump F2800E
dump F28040
```

Disable write protection, write `$55` to RAM byte 0, and read it back:

```text
write F2800E 0000
write F28040 5500
dump F28040
```

The first word printed at `00F28040` should be **`5500`**. Repeat with a second
pattern:

```text
write F28040 AA00
dump F28040
```

The first word should now be **`AA00`**. `0000` and `FF00` are additional test
patterns. The monitor dumps a larger region, including reserved/burst locations
and mirrored addresses, so only the first word is needed for this test.

Restore the saved RAM word first, then the saved write-protection word, using
the same `write` command.

The equivalent byte accesses in assembly are:

```asm
move.b  #$00,$00F2800E     ; Disable write protection
move.b  #$55,$00F28040     ; Write RAM byte 0
moveq   #0,d0
move.b  $00F28040,d0      ; Expect D0 = $00000055
```

## Monitor applications

Two standalone 68000 applications use the existing monitor UART and return to
its prompt with `TRAP #14`:

- [`rtc_set.asm`](../sw/app/asm/rtc_set.asm) asks for a decimal date/time in
  **`YYYY-MM-DD HH:MM:SS`** format, using years **2000–2099** and a 24-hour
  clock. It validates the calendar date (including leap days), calculates the
  weekday with Monday = 1, and then writes the RTC. Backspace/Delete edits the
  input; Escape cancels without changing the RTC. The oscillator is halted
  briefly during the writes, then started at the entered seconds value. The
  original write-protection setting is restored.
- [`rtc_get.asm`](../sw/app/asm/rtc_get.asm) prints the current date/time in the
  same format. It retries if seconds change while reading the individual
  registers, reports invalid/unsupported values, and identifies a halted clock
  when its seconds value can be decoded through the current conversion table.
  It does not write any RTC registers. Normal output is just the formatted
  date/time, followed by any halted-clock notice; diagnostic checkpoints have
  been removed.

Both applications include [`rtc_datetime.asm`](../sw/lib/asm/rtc_datetime.asm),
which includes the register constants in
[`mem_map_ds1302.asm`](../sw/lib/asm/mem_map_ds1302.asm). The shared reader loads
the RTC base address with `MOVEA.L #RTC_SECONDS,A0`, reads consecutive registers
with `MOVE.W (A0)+,Dn`, and extracts each upper byte. The longword operation
loads an address; the RTC reads themselves are word accesses. The setter uses
byte writes to update the RTC. The diagnostic probe applications are no longer
required.

Build both monitor images:

```sh
make target/app/rtc_set.bin target/app/rtc_get.bin
```

If picocom is already open in another terminal, load and run either application
directly while watching its output there:

```sh
make serial-load BIN=rtc_set.bin
# Or load the reader instead:
make serial-load BIN=rtc_get.bin
```

Alternatively, load the setter without running it, then open the serial terminal:

```sh
make serial-load BIN=rtc_set.bin RUN=0
make serial-open
```

At the monitor prompt, enter `run 10000`. At the application's prompt, enter
for example `2026-10-25 12:34:56` and press Enter. The application prints the
RTC's date/time after writing it. These input values are decimal; do not enter
BCD bytes or the shifted hexadecimal words used by the monitor's `write`
command.

For the same deferred-run workflow with the reader:

```sh
make serial-load BIN=rtc_get.bin RUN=0
make serial-open
```

Enter `run 10000` to print the date/time. Once the reader is loaded, run it
again after a few seconds to check that time advances. Both applications link
at `$10000`, so load and run them separately.
